# 과학SOS · 반례실험실 발표 안내

2026-09-18 · 사용자 승인에 따라 메인 배포합니다. 발표 교실은 https://science-sos.vercel.app/demo 에서 열 수 있습니다. 데이터는 유지하고 화면의 반복적인 테스트 표현만 정리했습니다.

## 한 문장

**과학SOS는 같은 오답 뒤의 서로 다른 이유를 읽고, 교사가 고른 반례를 통해 학생이 설명을 다시 쓰게 하는 과학 수업 도구입니다.**

핵심 장면은 **같은 오답, 다른 이유 → 교사 확인·수정·보류 → 반례 관찰 → 설명 수정 → 새 사례 재확인**입니다. 자료실·채팅·토론은 이 수업 흐름을 돕는 기능으로 짧게 소개합니다.

## 시연과 실제 연결의 구분

| 구분 | 발표용 `/demo` | 실제 수업 `/` |
| --- | --- | --- |
| 학생·자료 | 준비한 가상 학생 24명과 8개 수업의 예시 자료 | 로그인한 반의 Supabase 기록 |
| 시작 | 로그인 없이 교사·학생 역할 전환 | 실제 Supabase 인증 |
| 기록 | 이 브라우저에 저장, 시연 초기화 가능 | 서버에 저장, 역할·반별 접근 제한 |
| AI 표시 | 미리 준비한 분석·답변 예시 | 로그인된 PC의 공식 Cursor CLI 워커가 처리 |
| 실험 | 고정 조건의 시뮬레이션 및 관찰 기록 | 교사 승인 후 고정 실험 또는 탐구 활동 |
| 숫자의 의미 | 기능 설명용 가상 분포 | 테스트 계정 또는 해당 반의 실제 제출 분포 |

시작할 때 “지금 보시는 24명은 기능을 설명하기 위해 만든 가상 학급입니다”라고 밝힙니다. `/demo`에서 나타나는 분석과 채팅을 방금 생성된 실제 AI 응답이라고 설명하지 않습니다. 실제 AI 연결은 `/`에서 별도로 확인한 기능이며 PC 워커가 켜져 있어야 합니다. 어느 쪽의 시연 기록도 학습 효과를 입증한 실증 결과가 아닙니다.

| 25–40초 | 교사 확인 후 학생 역할, 나무·철 반례 | “교사가 실험을 열면, 80그램 나무는 뜨고 20그램 철은 가라앉는 반례를 봅니다. 학생은 무엇을 놓쳤는지 생각하고 설명을 다시 씁니다.” |
| 40–55초 | 처음 설명과 수정 설명, 새 사례 | “무거우면 가라앉는다는 문장이 물체와 액체의 밀도를 비교해야 한다는 설명으로 바뀌었는지 확인합니다. 새로운 물체에서도 설명할 수 있는지 다시 묻습니다.” |
| 55–60초 | 교사 화면 | “서술형 평가를 넓힐 때, 답을 쓰기 전에 조건을 비교하는 수업까지 함께 지원하겠습니다.” |

60초 안에 타이핑을 길게 하지 않습니다. 교사 승인과 학생 관찰을 직접 보여주고, 설명 비교는 준비된 완료 기록을 활용해도 됩니다. 이때 “다음은 같은 흐름을 마친 예시 기록입니다”라고 전환을 설명합니다.

## 3분 발표

### 0:00–0:35 · 문제와 대상

“과학 시간에 두 학생이 모두 ‘무거운 나무가 가라앉는다’고 답했다고 생각해 보겠습니다. 한 학생은 질량만 보고, 다른 학생은 크기를 근거로 답할 수 있습니다. 정오만 모으면 둘 다 같은 오답이지만, 다음에 물어볼 질문은 달라야 합니다. 과학SOS는 중학교 과학에서 학생의 이유와 설명 변화를 교사가 볼 수 있게 하는 도구입니다. 지금 보여드리는 명단과 답안은 발표를 위한 가상 학급입니다.”

### 0:35–1:15 · 교사가 다음 수업을 결정하는 장면

“교사는 반 전체의 답 분포와 ‘같은 답, 다른 이유’를 함께 봅니다. 학생 카드를 열면 예측과 이유 원문이 보이고, AI가 제안한 가설을 검토할 수 있습니다. 질량만 고려했는지, 크기만 봤는지, 액체 조건을 빠뜨렸는지 살펴봅니다. 가설은 확정 진단이 아닙니다. 교사가 확인하거나 수정해야 실험이 열리고, 근거가 부족하면 보류하고 이유를 더 받습니다. AI가 붙인 이름이 학생을 바로 분류하거나 실험을 자동으로 결정하지 않게 했습니다.”

### 1:15–2:05 · 반례와 설명 변화

“이제 교사가 질량만 본 학생에게 나무와 철을 비교하는 활동을 엽니다. 예시의 나무는 80그램, 100세제곱센티미터이고, 철은 20그램, 약 2.56세제곱센티미터입니다. 물에서 무거운 나무는 뜨고 가벼운 철은 가라앉습니다. 화면은 이 조건을 표현한 시뮬레이션입니다. 학생은 관찰을 바탕으로 처음 문장을 다시 씁니다. ‘무거우면 가라앉는다’에서 ‘물체와 액체의 밀도를 비교해야 한다’로 무엇이 달라졌는지 봅니다. 마지막에는 다른 물체에서도 설명이 성립하는지 다시 묻고, 교사는 조건 비교·관찰 증거·개념 설명을 확인합니다.”

### 2:05–2:35 · 구현 범위

“학생과 교사 화면, 인증과 기록 저장은 Next.js와 Supabase로 구현했습니다. 실제 연결 화면은 공식 Cursor CLI 워커를 통해 이유 분석과 자료 근거 채팅을 처리합니다. 발표용 화면의 답변은 미리 준비한 예시이고, 실제 AI 처리 화면과 분리했습니다. 자료실, 개별 피드백, 반별 토론도 이 수업 과정을 이어 줍니다. 현재 밀도 실험 세 가지가 있고, 다른 단원은 교사가 여는 탐구 질문과 관찰 기록으로 확장했습니다.”

### 2:35–3:00 · 정책 제안과 다음 검증

“다음으로 필요한 것은 현장 교사의 검토입니다. 문항과 반례, 루브릭을 함께 다듬고 짧은 수업에서 교사의 검토 부담과 학생 설명 변화를 확인하고 싶습니다. 교육청에는 개인 답안보다 어떤 조건에서 막혔고 어떤 지원이 필요했는지 최소한의 집계를 제공하는 방향을 제안합니다. 교육청 화면과 수업 효과 검증은 후속 과제입니다.”

## 대표 시연 순서

1. 운영 주소의 `/demo`에서 ‘시연 처음부터’를 눌러 이전 리허설 변경을 초기화합니다.
2. ‘교사로 보기’에서 밀도 수업을 선택합니다. ‘같은 답, 다른 이유’를 보여준 뒤 학생 01의 원문을 엽니다.
3. 학생 01은 교사 확인 대기로 시작합니다. 이유와 가설을 확인한 뒤 나무·철 비교 실험을 엽니다. 보류 흐름은 다른 예시 카드로 설명해 대표 학생의 흐름을 끊지 않습니다.
4. ‘학생으로 보기’로 바꾸고 ‘시연 학생’에서 학생 01을 선택합니다. 열린 실험을 관찰하고 설명을 수정합니다.
5. 새 사례를 확인한 뒤 교사 역할로 돌아와 처음 설명과 바뀐 설명을 비교합니다.
6. 여유가 있을 때 자료실·피드백·토론을 한 화면씩 보여줍니다. 60초 발표에서는 생략합니다.

입력할 설명 예시:

> 나무 80g은 떴고 철 20g은 가라앉았다. 질량만으로는 설명할 수 없다. 나무의 밀도는 물보다 작고 철의 밀도는 물보다 크므로, 물체와 액체의 밀도를 비교해야 한다.

자기 피드백 예시:

> 질량만 보고 부피와 액체의 조건을 놓쳤다.

새 사례 D04 설명 예시:

> A는 60÷100=0.6g/cm³로 물보다 밀도가 작아 뜬다. B는 30÷10=3g/cm³로 물보다 밀도가 커서 가라앉는다.

실제로 입력하지 않은 문장이나 미리 저장한 완료 기록을 현장에서 방금 생성된 학습 결과로 소개하지 않습니다.

## 구현 상태를 묻는 질문에 답하기

| 질문 | 답변 기준 |
| --- | --- |
| AI는 실제로 연결됐나요? | 실제 수업 경로에는 공식 Cursor CLI 워커가 연결되어 있습니다. 발표용 `/demo`는 준비한 예시입니다. 실제 응답을 추가로 보일 때만 `/`에서 제출합니다. |
| Cursor 크레딧으로 운영하나요? | 현재는 로그인된 PC에서 워커를 실행합니다. 호출별 비용이나 장기 운영비를 검증했다고 말하지 않습니다. |
| AI가 틀리면 어떻게 하나요? | 가설과 원문을 교사가 검토합니다. 근거가 부족하면 보류하고, 실제 호출 실패는 분석 불가로 표시해 직접 검토합니다. |
| 자료에 근거한 답변인가요? | 실제 채팅은 등록 자료의 원문 인용을 검증합니다. 현재 긴 자료 전체를 검색하는 구조는 아니며, 실시간 웹 검색 기능도 아닙니다. |
| 모든 단원에 실험 시뮬레이션이 있나요? | 밀도에 세 가지 고정 실험이 있습니다. 나머지 수업은 교사 승인 후 탐구 질문에 따라 확인한 내용을 기록합니다. |
| 학습 효과가 있나요? | 기능 시연과 통합 연결 검증 단계입니다. 학생 실증이나 인과적 효과를 확인한 결과는 없습니다. |
| 교육청에도 서비스하나요? | 최소 집계 제공을 제안하는 단계입니다. 교육청용 집계·내보내기 화면은 후속 범위입니다. |
| 휴대전화에서도 쓰나요? | 이번 발표는 PC 화면 기준입니다. 모바일 품질 검증 완료를 주장하지 않습니다. |

## 발표 전 리허설 체크리스트

- [ ] 주소가 `science-sos.vercel.app/demo`인지 확인한다.
- [ ] PC 브라우저의 100% 확대율에서 자료·학생 선택·교사 카드가 잘리지 않는지 확인한다.
- [ ] `/demo`의 가상 데이터 안내, 24명 명단, 수업 8개를 확인한다.
- [ ] ‘시연 처음부터’ → 교사 검토 → 학생 관찰 → 설명 수정 → 교사 확인을 끝까지 수행한다.
- [ ] 새로고침 후 시연 변경이 유지되고 초기화 후 기준 상태로 돌아오는지 확인한다.
- [ ] 실제 타이머로 60초 발표를 연습하고, 완료 예시 기록으로 넘어갈 장면을 정한다.
- [ ] 실제 AI도 보여줄 경우 PC 워커, 로그인, 인터넷, 응답 대기를 별도로 확인한다.
- [ ] AI가 늦어지면 “분석 대기 상태이며 교사가 직접 검토할 수 있습니다”라고 설명하고 준비된 시연으로 돌아간다.
- [ ] 기능 구현, 가상 데이터, 아직 하지 않은 실증을 구분해서 답한다.

## 브랜치와 배포 절차

1. 수정과 시연 데이터 보강은 `develop`에서 진행합니다.
2. 타입 검사·빌드와 PC 브라우저 시연을 확인하고 결과를 변경 내역에 기록합니다.
3. `develop`을 푸시하고 Vercel Preview가 준비된 뒤 `/demo`를 확인합니다.
4. 사용자가 메인 반영을 승인했습니다. 최종 검사 후 `main`에 반영하고 운영 배포를 확인합니다.
5. 발표용 브라우저 데이터는 실제 Supabase 학급에 복사하지 않습니다.
